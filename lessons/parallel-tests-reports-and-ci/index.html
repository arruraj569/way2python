Parallel tests, reports and CI

Framework & CI · Complete program, tricky exercise, and interview answers

First time writing Python?Start from zero →Read the punctuation guide ↗

The idea

Parallel runs need unique data, isolated browser sessions, and deterministic cleanup. Publish reports and diagnostic artifacts so a failure can be investigated later. CI should return a failing exit code when required checks fail.

A complete program to try.

BEFORE YOU RUN

Save the entire program in test_parallel_tests_reports_and_ci.py. Open a terminal in that file’s folder and activate your project’s virtual environment. Commands go in the terminal; the program goes in the .py file.

Install once in your activated environment: python -m pip install pytest.

Run: python -m pytest test_parallel_tests_reports_and_ci.py -q

On macOS/Linux outside a virtual environment use python3; on Windows use py. The beginner guide explains both.

COMPLETE PYTHON PROGRAM
import pytest
@pytest.mark.parametrize("value, expected", [(1, 1), (2, 4), (3, 9)], ids=["one", "two", "three"])
def test_square(value, expected):
    assert value * value == expected

def test_empty_collection():
    assert sum([]) == 0

  4. Line 4: Check value * value == expected. The program continues if this is true and raises AssertionError if it is false.

TRICKY PYTHON PROGRAM
from concurrent.futures import ThreadPoolExecutor
def build(worker):
    return f"user-{worker}@example.test"

with ThreadPoolExecutor(max_workers=3) as pool:
    emails = list(pool.map(build, range(3)))
print(len(emails) == len(set(emails)))
print(emails)

Run: python tricky_parallel_tests_reports_and_ci.py

True

Distinct worker IDs make distinct values inside this one run. Real CI runs also need a unique run identifier to avoid collisions with other runs.

INTERVIEW PRACTICE · EXPLAIN THE WHY

Talk it through.

Answer in your own words first. Then check the explanation and connect it to the programs above.

Why do tests that pass sequentially sometimes fail in parallel?

They may share records, accounts, output files, mutable fixtures or driver sessions. Give each test independent resources and unique identifiers, and preserve diagnostic artifacts rather than relying on order or retries.

Which common mistake can affect this program or test?

Do not make tests depend on execution order. Retries may diagnose flakiness but should not redefine a failure as success.
