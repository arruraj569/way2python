Requests sessions, headers and timeouts

HTTP & clients · Complete program, tricky exercise, and interview answers

First time writing Python?Start from zero →Read the punctuation guide ↗

The idea

A Session reuses connections and common settings. Explicit timeouts bound waiting; a connect/read tuple distinguishes connection setup from waiting for data. A context manager closes the client when its work is finished.

A complete program to try.

BEFORE YOU RUN

Save the entire program in requests_sessions_headers_and_timeouts.py. Open a terminal in that file’s folder and activate your project’s virtual environment. Commands go in the terminal; the program goes in the .py file.

Install once in your activated environment: python -m pip install requests.

Start the local API service first: python mock_api.py --port 8765 from the unzipped practice kit. Keep that terminal running, and run the program in a second activated terminal.

Run: python requests_sessions_headers_and_timeouts.py

On macOS/Linux outside a virtual environment use python3; on Windows use py. The beginner guide explains both.

requests_sessions_headers_and_timeouts.pyDownload program ↓
COMPLETE PYTHON PROGRAM
import requests
with requests.Session() as client:
    client.headers.update({"Authorization": "Bearer demo-token"})
    response = client.get("http://127.0.0.1:8765/users", timeout=(2, 5))
    response.raise_for_status()
    print("Session request passed")
EXPECTED RESULT
Session request passed.

How can session-level headers affect a supposedly independent request?

A Session reuses configured headers and cookies. Per-request settings can override them, and unintended shared session state can cross test boundaries. Use isolated client fixtures with explicit ownership and timeouts.

Which common mistake can affect this program or test?

A Requests timeout is not a guaranteed total wall-clock deadline for an entire multi-step scenario.
